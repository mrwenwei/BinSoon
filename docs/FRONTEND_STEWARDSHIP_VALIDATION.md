# #15–#17：提案審查、命名與認養

2026-10-20（Asia/Taipei）。以 `153a6e3` 為開始基準；只串接既有後端，不變更資料庫／API 業務規則，不部署、不新增雲端提案／票數／認養資料。

## 入口與行為

- 管理員 `#admin/proposals` 使用提案分頁與行政區／階段篩選；`#admin/proposals/<proposal.id>` 讀公開提案詳情的最新 ETag，以獨立 admin session 審查。市民詳情 `#proposals/<id>` 在管理員登入時提供審查連結。
- village 只能通過里辦評議至 evaluation；evaluation 只能通過評估至 survey；survey 才能確認示範設置至 installed。三階段可附必填原因拒絕；collecting／installed／declined 不提供設置審查操作。沒有跳關或加票控制。
- 操作先顯示影響與確認，確認期間若 ETag 改變，須取消後重新選擇；409／412／428 重新 GET，使用者檢視最新內容後才可明確重新確認。若原操作已不符合新階段，不能重新確認送出。
- 示範設置維持 proposal.bin_id 的同一 Bin，位置的 bin_type 仍是 proposed。列表與詳情重新讀取後端 placement_status，示範設置不表示現場已驗收；周邊 availability 由後端納入已設置未撤除的新增桶，仍含滿桶／未知／維修。
- 原提案人（citizen 且 mine）、installed、沒有 pending 命名時，可於市民詳情送 1..30 字桶名。顯示原提案名稱、最後申請名稱、命名狀態與已核准桶名；pending_name 不覆蓋 approved_name。
- 管理員於同一審查詳情核准或附必填原因退回命名；退回後原提案人可重送。競爭命名使 pending_name 改變時，舊核准意圖不能只換新 ETag 重送，必須取消、檢視新名稱並重新選擇。
- 公開桶名只在核准後由後端 GET 更新，與原提案 name、認養 display_name 分開。後端 ProposalRead 沒有命名退回原因欄位；本輪會提交必要原因，但不把其他結果原因冒充命名退回原因，也未新增後端欄位。
- `#adopt` 為市民自己的認養分頁及狀態篩選；`#adopt/<adoption.id>` 重新讀取自己的詳情與最新版本。桶詳情依 BinView.can_apply_adoption 提供 `#adopt/apply/<bin.id>`，已有 pending／active 則連回 my_adoption_id，公眾可見後端核准的認養名稱／身份／店家介紹。
- 申請支援居民／店家／學校／社區團體、公開名稱、店家介紹及完整 full／dumping／dirty 三項偏好。非店家 body.intro 一律空字串，待審期間沒有權益；同桶唯一 active、重複與核准競爭由後端拒絕，畫面重讀 BinView／申請狀態。
- `#admin/adoptions` 是管理員的待審／狀態／行政區分頁，`#admin/adoptions/<id>` 讀詳情 ETag 核准或附必填原因拒絕。競爭核准後顯示目前公開認養，不能繼續確認舊核准。市民／隊員不提供管理員控制或私有審查請求。
- 本人 pending 可確認撤回；active 可確認更新完整三項偏好（允許全 false）、附可選原因確認結束。結束說明關閉通知及後續新回報不再具有本次認養加倍資格，歷史保留；實際資格仍由後端判定，不在前端加點或產生權益。

## 共用命令

延續記憶體中的原命令，新增可選 POST／PATCH 方法（預設仍 POST）。PATCH 偏好更新在斷網／401／5xx 等未知結果重試時，保留原 method、序列化 body、key、ETag 與帳號。登入失效後同頁原帳號可重送；明確登出清除命令，不同帳號不能重送別人的命令。重新整理會失去未確認命令，應先查後端紀錄。
